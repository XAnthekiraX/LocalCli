# Analizador de Demo Frontend-Backend

Esta skill analiza un proyecto frontend y backend existente para generar una demo funcional independiente del backend, replicando la experiencia de usuario y los flujos principales usando las **mismas tecnologías** encontradas en el proyecto.

## Reglas Fundamentales

1. **NUNCA hardcodear archivos, datos ni tecnologías.** Todo debe ser descubierto mediante análisis del proyecto real.
2. **NUNCA modificar el proyecto original.** La carpeta del proyecto fuente es solo referencia para lectura.
3. **Crear una carpeta de demo separada** en la raíz con formato `Nombre_Demo` (ej: `Rey_Paletas_Demo`). El nombre se deriva del nombre del proyecto original.

### Derivar nombre de la demo

- Tomar el nombre del proyecto del `package.json` (campo `name`) o del nombre de la carpeta del proyecto
- Reemplazar espacios y guiones por guiones bajos
- Agregar sufijo `_Demo`
- Ejemplos:
  - Proyecto `rey-paletas` → `Rey_Paletas_Demo`
  - Proyecto `mi-app-admin` → `Mi_App_Admin_Demo`
  - Proyecto `Sistema de Gestión` → `Sistema_de_Gestion_Demo`

### Tecnologías a usar

- Detectar el framework frontend y usarlo
- Detectar el framework backend y usarlo para simular endpoints si es posible
- Detectar el sistema de estilos y usarlo
- Detectar el estado global y usarlo
- Detectar las llamadas API y reemplazarlas con mocks del mismo patrón
- Extraer las entidades de datos reales para crear datos de prueba

## Flujo de Trabajo

### Fase 1: Análisis Exhaustivo del Proyecto

1. **Identificar tecnología frontend**:
   - Revisar `package.json`, `yarn.lock`, `pnpm-lock.yaml`
   - Detectar framework: React, Vue, Angular, Svelte, Next.js, Nuxt, etc.
   - Detectar sistema de estilos: CSS modules, Tailwind, SCSS, Styled Components, etc.
   - Detectar gestor de estado: Redux, Zustand, Pinia, MobX, Context API, etc.
   - Detectar router: React Router, Vue Router, TanStack Router, etc.
   - Detectar librería de UI: Material UI, Ant Design, Chakra, Shadcn, etc.
   - Detectar HTTP client: fetch, axios, ky, got, etc.

2. **Identificar tecnología backend** (si existe en el repo):
   - Detectar framework: Express, Fastify, NestJS, Django, Flask, Laravel, Rails, etc.
   - Detectar ORM: Prisma, Sequelize, TypeORM, Mongoose, SQLAlchemy, Eloquent, etc.
   - Detectar base de datos: PostgreSQL, MySQL, MongoDB, SQLite, etc.

3. **Mapear estructura completa**:
   - Listar todas las carpetas y archivos del proyecto
   - Identificar la estructura de carpetas frontend y backend
   - Encontrar archivos de configuración (tsconfig, vite.config, webpack, etc.)

4. **Identificar páginas/rutas**:
   - Buscar archivos de enrutamiento según el framework detectado
   - Extraer todas las rutas, componentes asociados y metadata
   - Mapear jerarquía de navegación

5. **Identificar componentes**:
   - Listar todos los componentes reutilizables
   - Identificar componentes de página
   - Detectar patrones de composición (HOCs, render props, hooks, composables)

6. **Identificar entidades de datos**:
   - Buscar tipos/interfaces/modelos definidos en el proyecto
   - Extraer schema de entidades con sus campos y tipos
   - Identificar relaciones entre entidades (1:1, 1:N, N:M)

7. **Identificar llamadas API y servicios**:
   - Buscar toda la capa de servicios/API del frontend
   - Extraer endpoints, métodos HTTP, headers, body esperado
   - Identificar patrones de error handling
   - Detectar interceptores, middleware de petición

8. **Identificar autenticación y permisos**:
   - Buscar lógica de auth (login, register, logout, refresh token)
   - Identificar manejo de tokens (JWT, cookies, headers)
   - Detectar rutas protegidas y guards
   - Identificar roles y permisos

9. **Identificar flujos de usuario**:
   - Mapear los recorridos principales (onboarding, CRUD, settings, etc.)
   - Identificar formularios y validaciones
   - Detectar cambios de estado y transiciones
   - Identificar notificaciones y feedback al usuario

10. **Identificar dependencias externas**:
    - Servicios de terceros (Stripe, Firebase, AWS S3, etc.)
    - WebSockets o Server-Sent Events
    - SDKs externos
    - Archivos estáticos (imágenes, documentos, etc.)

### Fase 2: Generación de la Demo con las Mismas Tecnologías

**Usar exclusivamente las tecnologías detectadas en Fase 1.**
**Todos los archivos se crean dentro de la carpeta `Nombre_Demo/`, NUNCA en el proyecto original.**

1. **Crear estructura de la demo**:
   - Crear la carpeta `Nombre_Demo/` en la raíz del workspace (junto al proyecto original)
   - Copiar o recrear la estructura de carpetas del frontend dentro de `Nombre_Demo/`
   - Usar el mismo sistema de build (Vite, Webpack, etc.)
   - Usar la misma configuración de TypeScript/JS si existe
   - Crear mocks en la misma estructura que los servicios originales
   - **NUNCA crear, editar ni eliminar archivos en la carpeta del proyecto original**

2. **Crear capa de mock services**:
   - Crear un directorio `mocks/` o `services/_mock/` siguiendo la convención del proyecto
   - Para cada servicio/API existente, crear un mock que implemente la misma interfaz
   - Usar el mismo patrón de peticiones del proyecto (fetch, axios, etc.)
   - Mantener los mismos tipos/interfaz de respuesta
   - Simular delays de red (200-500ms)
   - Simular errores HTTP cuando sea apropiado (400, 401, 404, 500)

3. **Crear datos mock desde las entidades reales**:
   - Usar los tipos/interfaces encontrados para generar datos de prueba
   - Generar 10-15 registros por entidad principal con variaciones realistas
   - Crear relaciones coherentes entre entidades
   - Incluir casos edge (campos vacíos, valores extremos, Unicode, etc.)

4. **Implementar storage local**:
   - Usar el mismo patrón de estado del proyecto (Redux, Zustand, Pinia, etc.)
   - Persistir en localStorage cuando sea necesario
   - Implementar el mismo patrón de datos que usaría el backend

5. **Simular autenticación**:
   - Mantener la misma interfaz de auth del proyecto
   - Crear usuarios de prueba con roles variados
   - Usar el mismo mecanismo de tokens/sesiones detectado
   - Proteger las mismas rutas que el original

6. **Simular flujos principales**:
   - CRUD completo con las mismas operaciones del proyecto
   - Búsquedas y filtros con los mismos parámetros
   - Paginación con la misma lógica
   - Cambios de estado según las reglas de negocio encontradas
   - Validaciones de formularios con las mismas reglas

7. **Mantener intacta la capa visual**:
   - No modificar estilos CSS/SCSS/Tailwind existentes
   - No cambiar componentes de UI
   - Preservar layout, responsive design y animaciones
   - La demo debe ser visualmente indistinguible del original

### Fase 3: Documentación de Lo que No Se Puede Simular

Generar `DEMO_REPORT.md` en español documentando:

1. **Funcionalidades que requieren backend real**:
   - Listar cada endpoint con método, URL, headers, body y respuesta esperada
   - Explicar por qué no se puede simular (ej: validación server-side, datos en tiempo real, transacciones atómicas)

2. **Servicios externos que no se pueden replicar**:
   - Qué servicios de terceros dependen de credenciales reales o cuentas activas
   - Qué funcionalidades se pierden sin ellos

3. **Lógica de negocio compleja**:
   - Reglas que dependen de estado del servidor
   - Concurrencia y bloqueo de registros
   - Procesos batch o cron jobs

4. **Datos incompletos**:
   - Entidades que no pudieron ser mockeadas por falta de definición en el código
   - Relaciones que dependen de joins complejos de BD
   - Datos que requerirían seeding real

5. **Soluciones propuestas para cada limitación**:
   - Alternativa técnica viable
   - Prioridad de implementación (alta/media/baja)
   - Esfuerzo estimado
   - Dependencias necesarias

6. **Credenciales de prueba**:
   - Usuarios disponibles con sus roles
   - Credenciales de acceso
   - Permisos de cada usuario

## Instrucciones Críticas

- **NUNCA modificar el proyecto original** — solo leerlo como referencia
- **Crear carpeta `Nombre_Demo/` en la raíz** — todos los archivos de la demo van aquí
- **Toda la documentación debe generarse en español**
- **NUNCA hardcodear** datos, tecnologías ni estructura. Todo viene del análisis
- **Usar las mismas tecnologías** encontradas en el proyecto
- **Priorizar navegabilidad**: la demo debe poder recorrerse completamente
- **Crear datos variados** que cubran los casos de uso principales
- **Simular tiempos de carga** realistas
- **Manejar errores** de forma consistente con el patrón original
- **Mantener la lógica de estado** del frontend original
- **Documentar TODO** lo que no se pueda simular con soluciones concretas
