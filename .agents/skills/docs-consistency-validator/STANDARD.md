# AI Native Documentation Consistency Standard

All validation reports generated by this skill MUST follow these rules.

---

## Primary Goal

The validation report certifies coherence across the three representations of every data
field and entity, and is intended for both AI agents and human readers.

Every report must maximize:

- Determinism
- Explicitness
- Traceability (file + anchor)
- Consistency
- Machine readability

---

## Language

- Los reportes generados se escriben en **español** (idioma canónico del
  proyecto y de la documentación).
- Los campos `descripcion` y `fix_sugerido` se escriben en español.
- Usar español técnico; evitar lenguaje coloquial.
- La regla de idioma aplica a la **prosa**; el código, identificadores,
  nombres técnicos y JSON pueden permanecer en inglés.

---

## Severity Classification

Every finding has exactly one severity. Use the highest severity that applies.

| Severity | Meaning | Example |
|----------|---------|---------|
| `CRITICAL` | A contradiction of definition or type that breaks compilation, runtime, or the contract. | Column declared `uuid` in DB but DTO consumes it as `number`. |
| `ERROR` | A structural or contract inconsistency across layers. | Endpoint path/method differs between backend and frontend; entity references a FK with no table; a protected endpoint under a non-global security scheme has no security reference. |
| `WARNING` | A divergence risk or convention deviation without written justification. | Decimal without stated precision; deviating from the naming convention with no exception noted; a reference missing wiki link format; global security repeated per endpoint. |
| `INFO` | A consistency or coverage suggestion. | Minor duplication; an exposed field never visualized. |

## Estructura canónica (referencia de validación y migración)

La estructura de carpetas a la que se valida y se migra. Es la producida por
las skills de documentación. `ARCHITECTURE.md` vive siempre en la raíz de
cada capa y centraliza la información; las carpetas usan prefijo numérico
por jerarquía.

**`ai/docs/backend/`:**
```
ARCHITECTURE.md                   [raíz — centraliza toda la info del backend]
DECISIONS.md                      [raíz]
01-domain/        DOMAIN.md, BUSINESS_RULES.md
02-api/           API.md, auth.md, users.md, tasks.md (+ DTO por recurso)
03-security/      SECURITY.md
04-infrastructure/CONFIGURATION.md, INTEGRATIONS.md, EVENTS.md
05-quality/       TESTING.md, VALIDATION.md, ERRORS.md
```

**`ai/docs/frontend/`:**
```
ARCHITECTURE.md                   [raíz — centraliza toda la info del frontend]
DOMAIN.md                         [raíz]
01-user-flow/      <seccion>.md
02-components/     <COMPONENTE>.md
03-data/           FRONTEND-DATA.md
04-behavior/       FRONTEND-BEHAVIOR.md
05-state/          STATE.md
06-validation/     VALIDATION.md
07-errors/         ERRORS.md
08-auth/           AUTH.md
09-api-dependencies/ API-DEPENDENCIES.md
```

**`ai/docs/database/`:**
```
ARCHITECTURE.md                   [raíz — centraliza toda la info de la DB]
01-schema/        SCHEMA.md, TABLES.md, RELATIONSHIPS.md,
                  ENUMS.md, CONSTRAINTS.md, INDEXES.md
02-rules/         BUSINESS_RULES.md, DATA_FLOW.md
03-operations/    QUERIES.md, MIGRATIONS.md, SEEDING.md
```

**Regla:** esta estructura es la fuente de verdad. La validación compara la
estructura actual contra ella; la migración lleva la estructura actual a
coincidir con ella. Referencias a nombres viejos (`DATABASE.md`,
`00-BACKEND.md`, `00-FRONTEND.md`, `schema/`, `rules/`, `operations/`,
`user-flow/`, `components/`) son desviaciones estructurales.

## Hallazgos estructurales (categoría)

Los hallazgos de estructura se clasifican con la misma tabla de severidad.
Orientación de severidad:

| # | Hallazgo estructural | Severidad |
|---|----------------------|-----------|
| 1 | Falta `ARCHITECTURE.md` en raíz de una capa | ERROR |
| 2 | Entry point viejo presente (`00-BACKEND.md`, `00-FRONTEND.md`, `DATABASE.md`) | WARNING |
| 3 | Carpeta sin prefijo numérico (`user-flow/`, `schema/`, …) | WARNING |
| 4 | Documento en raíz que debe estar en subcarpeta | WARNING |
| 5 | Estructura flat/legacy (sin capas) | WARNING |
| 6 | Carpeta/archivo huérfano o residuo | INFO |
| 7 | Estructura canónica desactualizada vs realidad del proyecto | ERROR |
| 8 | Prosa narrativo en idioma distinto del español | WARNING |

Cada hallazgo estructural incluye en `fix_sugerido` el destino exacto según
la estructura canónica (p.ej. `mover STATE.md a 05-state/STATE.md`).

**Nota de idioma:** el hallazgo de idioma (fila 8) aplica a la prosa
narrativa y su `fix_sugerido` es "traducir a español". La traducción NO la
ejecuta esta skill; se marca como "requiere traducción" y se delega a otro
proceso.

## Hallazgos de optimización (categoría 8)

Los hallazgos de optimización detectan redundancias y oportunidades de
mejora. Incluyen el campo `optimizacion_sugerida` con la acción concreta.

| # | Hallazgo de optimización | Severidad | optimizacion_sugerida ejemplo |
|---|--------------------------|-----------|-------------------------------|
| 8.0 | Concepto duplicado en más de un archivo sin referencia wiki link | WARNING | "referenciar [[archivo-fuente]] en lugar de duplicar" |
| 8.1 | Información fragmentada de un concepto en múltiples archivos | INFO | "centralizar en [[archivo-mejor-ubicado]]" |
| 8.2 | Subcarpeta repite info que ya está en ARCHITECTURE.md de capa | INFO | "eliminar duplicación; ARCHITECTURE.md ya centraliza" |
| 8.3 | Archivo mezcla múltiples dominios no relacionados | WARNING | "separar en archivos por dominio" |
| 8.4 | Documento con exceso de jerga técnica o texto innecesario | INFO | "simplificar redacción" |
| 8.5 | Documentación de arquitectura sin SPEC correspondiente | WARNING | "crear SPEC antes de continuar" |

## Type Conversion Matrix

Default bridge between the three representations. The canonical, single source of truth for
this matrix is `~/.config/opencode/agents/documentation_agent.md` (`Convenciones de tipos y
naming`); this copy is the validation baseline. The project's own declared conventions
in `ARCHITECTURE.md` override these defaults when explicitly stated.

### A USAR (storage / SQL)

| A CONSUMIR (API / DTO) | A VISUALIZAR (UI / display) |
|--------------------------|------------------------------|
| `uuid` | `string` or `uuid` | opaque text / not displayed |
| `bigint` / `serial` | `number` (integer) | text / id |
| `numeric(p,2)` | `number` | currency with 2 decimals |
| `numeric(p,s)` | `number` | decimal with `s` decimals |
| `varchar(n)` | `string` (`stringN` if constrained) | text |
| `text` | `string` | text (multiline) |
| `boolean` | `boolean` | toggle / label |
| `timestamptz` | `string` ISO 8601 | localized date |
| `date` | `string` YYYY-MM-DD | localized date |
| `jsonb` | `object` | table / component |
| enum (`e_*`) | `string` (enum members) | select / label |

Rules:

- Every decimal MUST state `p,s`.
- Every `varchar(n)` MUST state `n`.
- Money values MUST display with exactly 2 decimals unless a different precision is
  declared.
- Dates MUST be consumed as ISO 8601 strings.

Any deviation not explicitly documented becomes a finding.

---

## Terminology and Casing

- A concept MUST use the same name across all documents. Never rename an entity or field.
- The DB layer uses `snake_case`; the API/DTO layer uses `camelCase`.
- The mapping `snake_case` ↔ `camelCase` must be deterministic: `created_at` ↔ `createdAt`.
- A definition MUST live in one authoritative document; other documents reference it,
  they do not duplicate it.

---

## Finding Schema

Each finding uses this structure (used in both Markdown and JSON):

```
severity        — CRITICAL | ERROR | WARNING | INFO
id              — reported-id like CSR-001, sequentially assigned
layer_origin    — database | backend | frontend | cross
file            — the document file(s) where the discrepancy appears
anchor          — section, table, or line reference within the file
concept         — the involved concept, formatted as Entity.field (or endpoint)
tipo_usar      — the storage type declared (or "n/a")
tipo_consumir  — the API/DTO type declared (or "n/a")
tipo_visualizar— the UI display type declared (or "n/a")
category        — name of the validation category (5.0, 5.1 .. 5.7, 8.0 .. 8.4)
descripcion     — explicit statement of the discrepancy
fix_sugerido     — the concrete suggested fix
optimizacion_sugerida — (opcional) accion concreta para optimizar documentacion
                        Solo se incluye en hallazgos de categoría optimización.
                        Formato: "referenciar [[archivo]] en lugar de duplicar"
                                 "centralizar en [[archivo]]"
                                 "eliminar duplicación; ARCHITECTURE.md ya centraliza"
                                 "simplificar redacción"
```

## Result Interpretation

- If any `CRITICAL` exists → verdict `INCONSISTENT`.
- If no `CRITICAL` and no `ERROR` → verdict `CONSISTENT` (WARNINGS/INFO/OPTIMIZATION may remain).
- The verdict derives only from `CRITICAL` and `ERROR` counts.
- Hallazgos `OPTIMIZATION` son sugerencias de mejora, no afectan el veredicto.

---

## Naming Conventions

- ID prefix `C` = critical, `E` = error, `W` = warning, `I` = info, each zero-padded.
- JSON keys are snake_case in the report and camelCase is used only for the concept/field
  references.
- Keep all output in Spanish and deterministic.
